# Coding and code-writing principles

Read this reference when the task includes writing, modifying, or restructuring code. Add the following constraints to the Work Contract when applicable:

1. **Match the project's established standards.** Follow the repository's language, framework, and open-source or industry conventions. Do not hide secrets merely for appearance when the project explicitly permits visible development configuration; do not introduce environment indirection without a real security or deployment requirement.
2. **Prefer the smallest complete implementation.** Do not add speculative features, compatibility paths, fallback branches, defaults, retries, or guards for scenarios that cannot occur on the current reachable call path and have no evidence in the contract, existing callers, documented interface, or observed failure. Handle real external boundaries such as user input, network, filesystem, process, and other I/O explicitly.
3. **Avoid defensive ceremony for known types and contracts.** Do not use `getattr`, `bool(x)`, `callable(x)`, excessive `isinstance` checks, broad `try/except`, or equivalent defensive patterns when the type and interface are already known. Catch exceptions only at real boundaries or where the core logic can take a defined, evidence-based recovery action.
4. **Use meaningful names and explicit interfaces.** Classes, functions, and variables should use concrete, understandable domain names that reveal the object's role, action, and responsibility at the call site. Do not create generic names or pass-through wrappers that obscure ownership. New project identifiers must not use leading-underscore names; Python protocol names, framework-required hooks, and precise overrides of existing interfaces are the narrow exceptions.
5. **Document decisions, not syntax.** Add docstrings to all methods and functions. A trivial method may use a one-line docstring; a complex function should document the non-obvious contract and follow the project's documentation conventions. Comments should explain implicit ownership, data source, execution order, cross-module handoff, or why a decision exists; do not restate the code.
6. **Keep control flow readable and contiguous.** Prefer a linear implementation that lets a reader follow the complete flow from input to result. Avoid scattering one piece of logic across many files or functions merely to make the structure look clean. A cohesive business function may be long when that keeps the behavior self-contained and understandable.
7. **Do not abstract by reflex.** A forwarding function without non-trivial logic should not exist. Do not introduce an abstraction for one use, one-off code, or a small amount of duplicated code when the abstraction only moves complexity without reducing it. Before extracting or splitting code, verify that it reduces reading or change cost rather than relocating it.
8. **Separate refactoring from behavior changes.** Structural refactoring is authorized only for code being written or when the task explicitly requests restructuring; it is not blanket permission to clean up unrelated existing code. Before deleting or moving a capability, confirm that existing callers no longer depend on it. If a refactor changes behavior, failure timing, compatibility, or observable output, state the difference and obtain the user's decision when the requirement does not determine acceptance.
9. **Prefer semantic correctness over surface cleanliness.** Expose errors early when they are provable; do not silently swallow them or defer them downstream. Do not optimize for fewer lines, more layers, or a cleaner-looking diff if the result increases indirection, reading cost, or behavioral risk.
10. **Use first-principles reasoning.** Start from the actual requirement, reachable data flow, caller contract, and failure evidence. Do not assume a familiar pattern is needed merely because it is common. If the target or behavior is unclear, stop and identify the exact ambiguity rather than encoding an unverified scenario into the code.
11. **Integrate structural changes deliberately.** When new functionality requires a substantial module or layer move, perform the necessary redesign and merge related paths instead of adding a parallel shim. After the change, remove obsolete duplication only when its callers and behavior have been verified. Do not perform broad cleanup unrelated to the requested outcome.

Before handoff for a coding task, review the diff for speculative guards, generic wrappers, unnecessary abstractions, scattered control flow, undocumented public behavior, invented identifiers, and refactoring that is unrelated to the requested outcome. Verify the actual call path and run the narrowest relevant tests plus any required type, lint, build, or integration checks.
